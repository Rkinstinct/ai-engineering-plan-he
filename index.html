תכנית חודש ל-AI Engineering

תשעה נושאים, ארבעה שבועות, ופרויקט אחד על נתוני אמת לכל נושא. הפרויקטים נשרשרים למאגר מסכם אחד.

הנחות: הנחות התכנית: כ-10 שעות בשבוע, בסך הכול כ-40 שעות בחודש (חמישה מפגשים של שעה בימי חול ומפגש אחד של 5 שעות בסוף שבוע, כל שבוע). עבודה על מחשב נייד רגיל עם Docker, ללא GPU וללא כרטיס אשראי. 40 שעות מספיקות להקיף את תשעת הנושאים ולהוציא פרויקט קטן שעובד מכל אחד, לא להגיע לשליטה עמוקה. התכנית בנויה כך שהפרויקטים נשרשרים לפרויקט מסכם אחד.

הכנה (חצי שעה, לפני מפגש 1):

  • מחשב עם Python 3.11 ומעלה, Git, Docker Desktop ו-uv להתקנת סביבות.
  • חשבון GitHub ציבורי למאגרי הפרויקטים (כבר קיים). מאגר אחד בשם ai-research-radar יצטבר לאורך החודש.
  • Ollama מותקן עם מודל קטן: ollama pull qwen2.5:3b (גרסאות 0.5b, 1.5b ו-3b קיימות בספריית Ollama). זה מודל השפה בכל הפרויקטים, ללא מפתח API וללא עלות.
  • קובץ LOG.md במאגר: בסוף כל מפגש שורה אחת על מה נבנה, מה נכשל, ומה נמדד.

איך הכול מתחבר: שרשרת הפרויקטים: שער ל-arXiv (1) מזין חיפוש סמנטי (2) שמזין מערכת RAG (3) שהופכת לכלי של סוכן (4), ואחריהם אריזה ו-CI (5), הערכה וניטור (6) ואופטימיזציית הסקה (7). הפרויקט המסכם (8) מחבר הכול, ו-(9) מגדיר איך לשמור על הרמה אחרי החודש.

כל הקישורים נבדקו ב-8.10.2026 והחזירו עמוד תקין. תיעוד משתנה, ולכן אם פקודה לא עובדת, הגרסה הנוכחית בתיעוד קובעת.

מדריך: בונים שרת MCP ראשון ב-Python (45 דקות)

משתלב בנושא 4 (מפגש 4 בשבוע 2). אפשר לעשות אותו לפני בניית שרת ה-MCP של הפרויקט.

MCP (Model Context Protocol) הוא פרוטוקול פתוח שבו אפליקציה עם מודל (הלקוח) מתחברת לשרת קטן שחושף לה כלים (פונקציות שהמודל יכול להפעיל), משאבים (נתונים לקריאה) ופרומפטים. אתה כותב את השרת פעם אחת, וכל לקוח שתומך בפרוטוקול יכול להשתמש בו. השרת שלמטה הוא תהליך מקומי שמדבר עם הלקוח דרך stdin ו-stdout (stdio), בלי פורט ובלי רשת.

1. התקנה

צור תיקייה והתקן את ה-SDK הרשמי. הגרסה הנוכחית בזמן הבדיקה היא mcp 2.3.0, ובה המחלקה נקראת MCPServer. בדוגמאות ישנות (ובחלק מהמדריכים) תראה FastMCP מ-mcp.server.fastmcp: זה של גרסה 1. אם אתה מעתיק קוד כזה, הצמד את החבילה ל-mcp<2.

uv init arxiv-mcp
cd arxiv-mcp
uv add "mcp[cli]" httpx

2. כותבים את השרת

שמור כ-server.py. כל פונקציה עם @mcp.tool() הופכת לכלי: סוגי הפרמטרים הם הסכמה, וה-docstring הוא התיאור שהמודל קורא כדי להחליט מתי להפעיל אותו, ולכן כתוב אותו כמו הוראה. הכלי כאן מחפש מאמרים ב-arXiv (בלי מפתח, ובקצב סביר: ראה את מגבלת שלוש השניות בפרויקט 1).

import logging
import xml.etree.ElementTree as ET

import httpx
from mcp.server import MCPServer

logging.basicConfig(level=logging.INFO)  # logging goes to stderr, safe for stdio
mcp = MCPServer("arxiv-search")

ATOM = "{http://www.w3.org/2005/Atom}"


@mcp.tool()
def search_arxiv(query: str, max_results: int = 5) -> str:
    """Search arXiv papers by keyword. Returns title, date, link and a short summary for each paper."""
    max_results = max(1, min(max_results, 10))
    resp = httpx.get(
        "https://export.arxiv.org/api/query",
        params={"search_query": " AND ".join(f"all:{w}" for w in query.split()), "max_results": max_results,
                "sortBy": "submittedDate", "sortOrder": "descending"},
        timeout=20,
        follow_redirects=True,
    )
    resp.raise_for_status()
    out = []
    for entry in ET.fromstring(resp.text).findall(f"{ATOM}entry"):
        title = " ".join(entry.findtext(f"{ATOM}title", "").split())
        summary = " ".join(entry.findtext(f"{ATOM}summary", "").split())[:300]
        out.append(f"{title} ({entry.findtext(f'{ATOM}published', '')[:10]})\n"
                   f"{entry.findtext(f'{ATOM}id', '')}\n{summary}")
    return "\n\n".join(out) or "No results."


if __name__ == "__main__":
    mcp.run()

3. כלל אחד שאסור לשבור

בשרת stdio לעולם אל תדפיס ב-print: stdout הוא ערוץ הפרוטוקול, וכל טקסט נוסף שובר אותו. כתוב ללוג דרך מודול logging (הוא כותב ל-stderr). זה נכון גם כשהשרת נראה תקין בהרצה ידנית וקורס בתוך לקוח.

# test_client.py (הרץ: uv run python test_client.py)
import asyncio
from mcp import Client, StdioServerParameters

params = StdioServerParameters(command="python", args=["server.py"])

async def main():
    async with Client(params) as client:
        tools = await client.list_tools()
        print([t.name for t in tools.tools])
        result = await client.call_tool("search_arxiv", {"query": "agent evaluation", "max_results": 2})
        print(result.content[0].text[:400])

asyncio.run(main())

מוסיפים את השרת לקובץ claude_desktop_config.json תחת mcpServers (macOS: ~/Library/Application Support/Claude/, Windows: %AppData%\Claude\), ומפעילים מחדש את האפליקציה. ייתכן שצריך נתיב מלא ל-uv (which uv או where uv).

{
  "mcpServers": {
    "arxiv": {
      "command": "uv",
      "args": ["--directory", "/ABSOLUTE/PATH/arxiv-mcp", "run", "server.py"]
    }
  }
}

7. מה מתאים לרישיון המוגבל שלך

הרישיון בארגון שלך: Claude Chat ו-Claude Code בלבד, בלי connectors ובלי plugins. אז: (א) הלקוח של Python מסעיף 4 והסוכן שלך מנושא 4 עובדים מול השרת ישירות, בלי תלות ברישיון בכלל, וזה הנתיב הבטוח לתרגול. (ב) Claude Code עם claude mcp add הוא ההגדרה המקומית של הכלי עצמו ולא connector מהספרייה של Anthropic, אז הוא הנתיב הסביר לשימוש עם Claude, אבל לא נבדק מול מדיניות הארגון שלך: אם מנהל החשבון חוסם שרתי MCP, הפקודה לא תעזור. בדוק זאת פעם אחת לפני שתסתמך עליו. (ג) Claude Desktop ו-connectors של claude.ai כנראה לא מתאימים לרישיון הזה, ואל תבנה עליהם.

נושא 6: הערכה, ניטור ובטיחות

4 שעות (מפגשים 4-5 ושעתיים ממפגש 6)

שלוש שאלות שונות: האם המערכת נכונה (הערכה), האם הנתונים השתנו (סחיפה), והאם היא הוגנת ובטוחה (הטיה והתקפות). לכל אחת כלי ומדד.

מה עושים, מפגש אחר מפגש

  • מפגש 4 (שעה): סחיפה. הורד את קובץ ינואר ופברואר 2026 של Yellow Taxi, והרץ דוח Data Drift של Evidently בין החודשים על המאפיינים של מודל פרויקט 5. כתוב פסקה: האם הסחיפה מצדיקה אימון מחדש.

נושא 7: הסקה מתקדמת ואופטימיזציית עלות

3 שעות (שלוש שעות אחרונות במפגש 6)

מה משפיע על מהירות ועלות הסקה: קוונטיזציה, גודל מודל, batching ומטמון. על CPU בלבד תמדוד קוונטיזציה ומטמון סמנטי, ותקרא על vLLM (דורש GPU) כדי להבין serving יעיל.

מה עושים, מפגש אחר מפגש

  • מפגש 6, שעה ראשונה: קרא את README הקוונטיזציה של llama.cpp ואת סקירת הקוונטיזציה של Hugging Face. רשום מה ההבדל בין Q4 ל-Q8 מבחינת זיכרון, מהירות ואיכות.
  • מפגש 6, שעה שנייה: הרץ את אותו מודל ב-Ollama בשתי רמות קוונטיזציה, מדוד tokens לשנייה וזיכרון, והרץ עליהן את 30 השאלות של פרויקט 3. השווה איכות לפי הבדיקה מנושא 6.
  • מפגש 6, שעה שלישית: מטמון סמנטי. משוך כ-500 כותרות שאלות אמיתיות מ-Stack Exchange API (אתר datascience) כזרם שאילתות, והטמע כל אחת עם אותו מודל. אם דמיון הקוסינוס לשאילתה שכבר נענתה עולה על סף, החזר תשובה שמורה. מדוד hit-rate בספים 0.80, 0.85 ו-0.90.

נתונים אמיתיים: כותרות שאלות אמיתיות מ-Stack Exchange API (אתר datascience.stackexchange.com), וקובץ 30 השאלות שלך.

מה בונים: טבלת השוואה של שתי רמות קוונטיזציה (זיכרון, tokens לשנייה, ציון על 30 שאלות), ושכבת מטמון סמנטי לשירות ה-RAG עם עקומת hit-rate לפי סף.

מה מתקבל: דוח של עמוד אחד עם שתי טבלאות והמלצה: איזו קוונטיזציה ואיזה סף מטמון.
